# Smart Health Assistant 技术报告

版本：v1.1
项目类型：医疗辅助问诊研究型原型
核心技术：Python、FastAPI、LangGraph、DeepSeek API、Chroma、BM25、MySQL、Redis、Docker

## 1. 项目概述

Smart Health Assistant 面向健康咨询、预问诊、检验报告解读、用药咨询和医保信息查询场景，提供带安全校验和来源追踪的辅助信息服务。系统不进行临床诊断、处方开具或急诊替代处置，输出仅用于帮助用户整理信息和选择下一步就医行动。

项目的重点不是让单个大模型直接回答问题，而是将一次请求拆分为可执行、可校验、可回放的任务：由 Supervisor 负责意图识别和任务规划，领域 Agent 在有限权限内执行，Verifier 独立检查结果，最终由响应层组织用户可读答案。

当前线上问诊链路使用 DeepSeek API。面向 GRPO 微调动作模型的五动作适配层已保留为独立能力，但当前问诊主链路不依赖该模型。

## 2. 系统边界与目标

### 2.1 目标

- 优先识别急症红旗，避免普通问答覆盖安全信号；
- 将复合请求拆成多个领域任务，支持依赖控制和无依赖任务并行；
- 为不同 Agent 隔离提示词、上下文和工具权限；
- 使用中文医学资料、药品资料和医保资料增强回答；
- 为每个任务保留状态、工具调用、结果和证据来源；
- 在失败时进行有限重试、局部修复或人工接管；
- 通过离线评测验证候选策略，不在线自动修改生产链路。

### 2.2 非目标

当前版本不自动确诊、不替代医生或药师、不自动开具处方或个性化剂量，不把用户生成内容直接写入知识库，也不允许候选策略在线修改急症规则、工具权限或安全阈值。

## 3. 总体架构

```text
用户 / 前端
    │ SSE 流式事件、卡片、暂停恢复
    ▼
FastAPI 会话与接口层
    ▼
Supervisor AgentLoop
    Intent Gate → Planner → Executor → Verifier → Responder
                         ▲                    │
                         └── 局部修复 / 重规划 ┘
    ▼
领域 Agent
    symptom / report / pharmacy / insurance / advisor
    ▼
工具与知识层
    Skills、RAG、规则引擎、MCP、用户数据工具
    ▼
MySQL / Redis / OpenTelemetry + Jaeger / 离线评测
```

系统本质上是受约束的 Agentic Workflow：LangGraph 负责状态图和调度，领域 Agent 在各自边界内进行有限的工具选择、信息补充和失败处理。它不采用多个模型自由辩论，因为医疗场景更需要权限隔离、可审计和确定性安全控制。

## 4. 一次请求的执行流程

### 4.1 Intent Gate

请求先经过确定性急症规则，命中高风险信号时直接进入安全响应；未命中时由 DeepSeek 进行结构化意图识别，将请求归类为 `pure_chat`、`health`、`mixed` 或 `emergency`。模型输出使用结构化 Schema 校验，服务异常时采用保守兜底，不把模型故障视为安全通过。

### 4.2 Planner

Planner 将规范化请求转换为任务 DAG。任务至少包含：任务 ID、目标 Agent、目标、输入切片和依赖任务。生成后执行以下检查：

- ID 唯一，依赖存在且无环；
- Agent 属于允许的领域集合；
- 任务数量和重试次数受限；
- 输入只包含目标任务需要的信息；
- 不得生成诊断、处方或越权剂量任务；
- 无依赖任务可以并行，有明确风险依赖的任务必须串行。

示例：

```text
symptom_agent  ──────┐
                     ├─> verifier ─> responder
report_agent   ──────┤
insurance_agent ─────┘
```

### 4.3 Executor

Executor 按 DAG 计算执行波次，将同一波次的独立任务并行运行，并为每个领域 Agent 构造最小输入切片。它统一处理工具调用、重试、超时、任务租约、暂停恢复和结果持久化。某个任务失败时，不默认重跑整张图，而是标记受影响的下游任务，在修复轮次内局部重跑。

### 4.4 Verifier 与响应层

Verifier 使用独立审计视图，只读取原始请求、任务结果信封、工具调用日志、证据元数据和安全规则结果，不读取领域 Agent 的完整内部消息。它输出 `pass`、`partial`、`fail` 或 `unsafe`，并给出需要修复的任务和问题指纹。

通过后，Responder 将结构化结果组织成自然语言和前端卡片；不通过时执行定向修复、保守降级或 handoff。达到重试上限后不继续循环。

## 5. 领域 Agent 与 Skill

领域 Agent 具有独立的系统提示、工具白名单、上下文边界、停止条件和输出契约：

| Agent | 职责 | 典型工具 |
|---|---|---|
| `symptom_agent` | 症状信息收集、风险分流、追问 | 红旗规则、风险评估、患者档案 |
| `report_agent` | 检验指标和报告辅助解读 | OCR、参考范围查询、RAG |
| `pharmacy_agent` | 药品信息、相互作用和用药安全 | 药品库、相互作用检查、RAG |
| `insurance_agent` | 医保账户和政策信息查询 | 用户业务数据、政策检索 |
| `advisor_agent` | 通用健康知识和生活方式科普 | RAG、受控搜索 |

Skill 是可复用的领域能力，不等同于 Agent。Skill 通常提供一个受约束的函数或工具；Agent 负责在子目标范围内选择工具、组合结果、请求补充信息并按契约结束。当前系统采用“Supervisor + 领域 Agent + Skill/Tool + Verifier”的混合形态，重点是可控协作，而不是为了名义上的多 Agent 增加自由对话。

领域结果统一为结果信封：

```json
{
  "agent": "report_agent",
  "status": "completed",
  "summary": "结构化的领域结果",
  "evidence": [{
    "tool": "knowledge_base.aretrieve",
    "source_type": "rag_document",
    "source_ids": ["source-id"],
    "version": "knowledge-version"
  }],
  "risk_level": "unknown",
  "uncertainty": [],
  "next_action": "必要时建议就医",
  "attempt_count": 1
}
```

## 6. 医疗安全控制

安全控制层采用“模型决策 + 确定性规则 + 工具结果”的混合方式，模型不能覆盖确定性安全结果。主要机制包括：

- 急症红旗识别和 `emergency veto`；
- 风险分级和高风险场景升级；
- 追问上限、任务超时和重试上限；
- 引用来源过滤和证据缺失降级；
- 诊断、处方、个性化剂量等越权表述拦截；
- 安全失败时优先输出立即就医或人工咨询建议。

当前红旗离线测试包含 48 条人工审核的合成案例，结果为 Precision 96.3%、Recall 86.7%、F1 91.2%、分级准确率 89.6%。该数据集规模有限，不能代表临床分布，也不应被表述为临床验证结果。

## 7. RAG 知识库

### 7.1 数据与索引

知识库以中文医学资料为主，覆盖疾病知识、检验参考范围、药品说明与相互作用、医保政策等。来源经过清洗、分段和元数据补充后建立索引；每条内容保留来源 ID、类型、版本和章节等信息。

当前向量检索后端使用 Chroma，关键词检索使用 BM25。采用父子块结构：子块用于精确召回，父块用于恢复完整上下文；同一父块只展开一次，避免多个子块命中造成重复上下文。

### 7.2 检索链路

```text
查询规范化
  → BM25 召回 + Dense 召回
  → RRF 按排名融合
  → MMR 去重重排
  → 父块聚合
  → 上下文与来源注入 Agent
```

RRF 是多路结果融合方法，MMR 是融合后的相关性与多样性重排方法，两者职责不同。当前配置优先控制候选数量和上下文长度，不把 MMR 当作独立召回算法。

### 7.3 当前检索评测

已有 100 条模板生成并人工审核的查询集，记录过来源级 Recall@1 48%、Recall@3 77%、Recall@5 79%、MRR 0.626、平均延迟约 114 ms。该评测只衡量来源定位，不代表医学答案正确性；查询集规模和分布仍有限，后续需要增加真实中文临床指南、药品和医保资料构成的人工标注集，并补充端到端引用忠实度评测。

## 8. 会话、可观测性与数据边界

- MySQL 保存会话、任务、评估和演进状态；
- Redis 用于短期状态、缓存和任务协调；
- FastAPI + SSE 向前端推送节点状态、工具调用和卡片事件；
- OpenTelemetry + Jaeger 记录节点耗时、工具名称、状态和资源指标；
- 默认不把医疗原文和图片写入通用 Trace；
- 轨迹按“原始请求、任务计划、工具事件、结果信封、Verifier 结论、最终响应”组织，支持回放和失败归因；
- 离线评测可显式捕获有限 RAG 原文用于 Judge，持久化前剥除原文，线上请求不会开启该开关。

## 9. 评估驱动的受控演进

这里的“自进化”不是在线自改模型，而是离线候选策略演进：

```text
轨迹 / 反馈
  → 脱敏 FailureCase
  → 失败模式归因
  → Candidate Skill / Prompt / 检索配置
  → 冻结评测集回放
  → baseline / candidate 对照
  → 安全与资源门禁
  → 人工审核、版本化和回滚
```

### 9.1 策略的存在形式

当前候选主要以版本化配置或 Skill Proposal 存在，例如任务顺序约束、追问策略、检索参数和安全阈值候选；不是让模型在线修改参数，也不是自动改写生产代码。候选只有在离线回放、人工审核和发布流程完成后才可能进入受控环境。`emergency veto`、红旗规则和工具权限不能被候选放宽或删除。

### 9.2 轨迹与失败案例

一次轨迹至少包含请求 ID、意图、任务 DAG、Agent 执行状态、工具调用、证据元数据、Verifier 结论、重试/修复历史、成本和延迟。失败归因覆盖错误路由、任务失败、重复追问、提前终止、证据缺失、潜在安全违规和资源超限。原始医疗内容进入离线评估前应脱敏，并由人工确认。

### 9.3 冻结评测集与门禁

冻结集是版本固定、不可因候选结果临时修改的离线样本集合。每条样本应记录来源、许可、去标识状态、人工复核状态、期望 Agent、任务依赖和证据锚点。当前真实 Graph 对照集仍为 9 条人工构造样例，尚未达到 80–120 条公开资料适配且人工标注的冻结集标准。

候选门禁包括：

- 安全规则和急症分流不得回归；
- 关键路由和任务通过率不得下降；
- 引用来源和证据质量不得下降；
- 平均 token 成本、延迟增量受预算限制；
- 候选必须可解释、可版本化、可回滚；
- LLM Judge 只用于离线诊断，不能单独触发线上发布。

当前已实现离线 Planner 合同检查、来源可追溯检查和可选 LLM Judge。Judge 输出不完整、超出 Schema 或引用未知证据 ID 时会被标记为无效，不计入忠实度分数，也不会自动生成可发布 FailureCase。

## 10. 当前评测与已知限制

已具备：

- 48 条安全边界案例及红旗规则评测；
- 100 条 RAG 初步查询集及来源级指标；
- Agent DAG 结构、任务覆盖和证据来源检查；
- baseline/candidate 真实 Graph 成对运行器；
- 失败候选生成、离线 Judge 和相关测试；
- 现有项目自动化测试与工程级契约测试。

当前不能声称：

- 自进化已经带来稳定效果提升；
- 已完成 80–120 条真实中文医疗冻结集；
- RAG 来源召回等同于临床答案正确；
- 已证明多 Agent 相比单 Agent 的端到端收益；
- 已证明故障降级后的线上可用性提升。

最近一次单案例 smoke run 中，baseline 和 candidate 均通过既有门禁，分数变化为 0；该结果只证明评测链路可运行，不构成总体性能结论。后续应优先扩充人工标注冻结集，增加 Planner 规划质量、端到端引用忠实度，并进行 Supervisor/多 Agent 与单 Agent 的受控消融实验。

## 11. 部署与复现

后端启动前配置模型和数据库环境变量，使用 Chroma 知识库索引；前端通过 Vite 启动，后端通过 FastAPI/Uvicorn 提供接口。典型流程：

```powershell
cd backend
uv sync
uv run python -m rag.ingest
uv run uvicorn main:app --reload --port 8000
```

运行相关评测：

```powershell
cd backend
uv run python -m unittest discover -p "test_*.py"
uv run python -m evals.run_self_evolution_eval --case regression-report --graph-timeout 90
uv run python -m evals.run_self_evolution_eval --llm-judge --case regression-report
```

评测结果写入 `backend/evals/reports/`。运行完整评测前，应确认模型服务、Chroma 索引和所需外部工具可用，并将超时、服务错误和 Judge 无效输出与能力指标分开记录。

## 12. 结论

Smart Health Assistant 当前是一个以医疗安全为优先、以 LangGraph 状态图为核心、以领域 Agent 和受控工具协作为主要实现方式的研究型原型。它的价值在于把问诊任务、证据、规则、失败和评测统一到可追踪流程中，而不是声称已经完成临床级智能诊疗或在线自动自进化。
