## 一、Agent 编排

### Q1. 为什么用 Plan-and-Execute，而不是 ReAct 或者一个强模型一把梭？

**答：** 因为我的任务本质是"多领域可分解"的，而不是"单线程探索"的。

三条具体理由：

1. **任务天然是 DAG。** "帮我看看这份体检报告，顺便说说我吃的降压药和报告里的肾功能指标有没有关系"——这要拆成报告解读 + 用药信息 + 交叉推理，其中报告解读和用药查询互相不依赖，可以并行。ReAct 是"一步一调用"，没法表达"这两件事同时做、第三件事依赖前两件"。
2. **安全门禁需要一个明确的中间点。** 我的架构是 `intent_gate → planner → executor → verifier → responder`。计划生成之后、真正执行之前，我能对整张任务图做一次安全与权限校验；ReAct 没有这个"计划"这个可审查的中间产物，风险只能事后兜。
3. **成本和确定性可控。** 计划是一次结构化输出，执行阶段大多数节点是确定性调度，只有领域节点内部才调模型。ReAct 的循环长度不可预知。

**代价我很清楚：** 计划多一次 LLM 调用；纯闲聊或单领域简单问题时，这套编排是纯开销。所以我在 `intent_gate` 就把它分流了——`emergency` 直接短路进安全响应，不进 planner；`chat` 和 `health` 才走完整的计划-执行-校验链路，由 planner 决定派哪个领域 Agent。

**会被追问：** 那 `intent_gate` 判错了怎么办？——它是结构化输出 + 置信度，低置信度时按 `health` 走重链路，宁可贵一点不丢安全。判错分流的兜底是确定性急症规则的独立检查，不依赖意图。

### Q2. 这五个节点里，哪些是真 agent，哪些只是函数？你怎么定义"多智能体"？

**答：** 严格说，我这个系统是 **Supervisor + 能力模块**，不是分布式多智能体。我在简历里写"多智能体协作架构"，指的是按能力和工具边界划分出可以独立决策的节点，由 Supervisor 编排——这个说法我要主动把边界讲清楚，不然容易被理解成我夸大了。

逐个说：

| 节点 | 性质 | 说明 |
| --- | --- | --- |
| `intent_gate` | 单次 LLM 决策 | 结构化分类，无循环、无工具，只是决策点 |
| `planner` | **真 agent** | 结构化 LLM 产出任务 DAG，自主决定用哪些能力、依赖怎么连 |
| `executor` | 确定性调度 | 按 DAG 拓扑分批、并发调用，本身不做决策 |
| `verifier` | **混合** | 确定性检查（schema、引用、安全标记）+ LLM 判证据是否充分 |
| `responder` | 受约束生成 | 有 LLM 生成，但证据、安全结论、格式都被上游锁定 |

五个领域模块（问诊 / 报告 / 药品 / 医保 / 通用）里，只有问诊是真正的多轮自主循环（`ask → check → search → answer`，自己决定下一句问什么）；报告、药品、医保更接近"带工具的专家函数"。

**共享与隔离：** 共享的是 `task_queue`、`task_results`、安全标记、记忆上下文这些 schema 化的状态；隔离的是每个节点自己的工具调用轨迹和中间草稿，不互相污染。

**会被追问：** 那你为什么不叫它"多智能体"？——因为智能体的核心判据是"能在不确定环境里自主决定下一步"，我只有 planner 和问诊节点满足。诚实地讲这个区别，比被追问到才承认要好。

### Q3. 重规划上限设 2 是怎么来的？两次都失败怎么办？

**答：** 2 是实测调出来的，不是拍的。

触发条件是 verifier 返回 `partial` 或 `fail`，并且失败原因能定位到具体子任务（比如报告 Agent 返回了结论但没给证据）。我的观察是这类失败绝大多数一次重规划就解决，第二次之后成功率明显掉——因为再重试已经不是"计划错了"，而是"这个能力就是做不到"，继续循环只会烧钱。

所以真正的限制是三层叠加的：

- 任务级：`MAX_PLAN_TASKS=6`，`MAX_REPLANS=2`
- 运行时级：`RuntimeBudget(max_steps=80, max_tool_calls=32, timeout_seconds=120)`（`backend/agent_runtime.py`）
- 检索级：`max_rounds=3`

超过任何一层，verifier 收敛到 `exhausted`，走 responder 输出**保守回答 + 明确说明缺什么**，绝不编一个完整答案。这是医疗场景的底线：宁可说"我现在拿不到 X 证据"，也不能硬答。

**会被追问：** 那"说明缺什么"是模板还是生成的？——是把 `missing_facets` 和失败的子任务结构化传给 responder 生成的，不是固定话术。

### Q4. "按依赖并行调度"具体怎么做的？两个 Agent 结论冲突谁仲裁？

**答：** 依赖关系是 planner 显式产出的：每个 `PlannedTask` 带 `depends_on` 字段。executor 按拓扑排序分批，同一批里用 `asyncio.gather` 并发，有依赖的等前驱写回 `task_results` 再跑。

结果合并按 `task_id` 分键，天然不覆盖；responder 阶段做统一综合。

**冲突仲裁现在是这样，我要如实说清楚：** 还没有独立的仲裁 agent。

优先级是：**安全结论 > 证据强度 > LLM 综合**。也就是说，任何一个子任务触发急症红旗或安全约束，直接压过其他所有结论——这是硬规则；如果只是两个 Agent 说法不一致（比如问诊倾向自我照护、药品提醒该就医），由 responder 综合，并在需要时把分歧显式暴露给用户而不是悄悄选一个。

**会被追问：** 这是不是太弱了？——是。真要做得更硬，应该引入一个 verifier 级的冲突检测：当两个子任务的 triage level 差两级以上时强制升级到保守侧。这是我下一步要补的。

## 二、Agentic RAG

### Q5. 证据充分性是 LLM 判的，凭什么信它？

**答：** 因为我没让它单独说了算，LLM 只是一个信号源，外面裹了三层约束（`backend/agentic_rag.py`）：

1. **判据是结构化的，不是让它自由发挥。** LLM 必须输出 `{sufficient, missing[], next_query}`。我要求它显式列出"缺哪些 facet"，只要 `missing` 非空就不算充分——这比让它只说"够了"要难糊弄得多。
2. **它有下限约束。** 即使 LLM 说 sufficient，也要 `len(seen) >= min_sources(=2)` 才算数。单条来源撑不起一个多面问题。
3. **有硬上限和无进展保护。** `max_rounds=3`；如果一轮检索没带回任何新 source_id，就直接跳到下一个缺失 facet，不做重复检索；控制器模型挂了就回退到确定性的 facet 规则，保证评测可复现。

每一步的 stop_reason 都写进 trace（`llm_evidence_sufficient` / `evidence_sufficient` / `max_rounds` / `no_more_queries`），出了问题能复盘是模型判的、规则判的还是预算耗尽的。

**这里我不粉饰：** 100 条上 `sufficient_rate` 只有 0.62，也就是超过三分之一的运行是耗到 `max_rounds` 才停的，说明这个控制器判"够了"的时机并不理想——它更常见的问题是**判不够**，而不是自我感觉良好。这是我下一步要调的。

### Q6. 消融实验的口径是什么？来源级 +1pp 有意义吗？

**答：** 先把口径讲清楚：

- **数据集：** `evals/rag_cases.jsonl`，100 条人工梳理的"问题 → 期望来源章节"映射集。仓库里那个 500 条文件是这 100 条的确定性 5 倍合成扩展，我只用它跑稳定性，**报数一律用 100 条**。
- **Baseline：** 一次 `HealthKnowledgeBase.retrieve` 调用，BM25 + 稠密向量双路召回，取 top-3。
- **Agentic：** 最多 3 轮，每轮由 DeepSeek 判证据是否充分、生成追问 query，最后对候选证据做一次 LLM 重排。

| 指标 | Baseline | Agentic | 差值 |
| --- | --- | --- | --- |
| 章节级 Recall@1 | 0.26 | 0.47 | +0.21 |
| 章节级 Recall@3 | 0.35 | 0.52 | **+0.17** |
| 来源级 Recall@3 | 0.92 | 0.93 | +0.01 |
| MRR | 0.3155 | 0.4995 | **+0.184** |
| 平均延迟 | 4.6s | 28.1s | +23.5s |
| 平均检索次数 | 1.0 | 1.46 | +0.46 |

（来源：`backend/evals/reports/rag_agentic_comparison_100_deepseek_rerank.json`）

**关于 +1pp：** 我不认为它有意义。100 条样本上来源级 baseline 已经 92%，这个指标本身已经接近天花板，1pp 完全在噪声量级。真正有信号的是**章节级 Recall@3 的 +0.17（绝对值）和 MRR 的 +0.18**——前者说明多轮检索确实捞回了单轮捞不到的内容，后者说明排序质量是真的改善了，而不是靠多捞几条凑数。

**还有一个必须说的：** 简历里"相对提升 0.17"这个措辞是错的，0.17 是绝对值，相对提升接近 49%。这个我已经在文档里改正，面试前需要同步改简历。

**会被追问：** 做过显著性检验吗？——没有。100 条自建集、单次运行，我只能说差异方向一致、幅度远大于噪声，不能说统计显著。要补的话是多次运行报均值±方差。

### Q7. rerank 和被评测的模型都是 DeepSeek，这个 Judge 可信吗？

**答：** 这是个真问题，我分三层回答。

**第一，同源确实有偏置。** 检索控制器和 rerank 用的是 `deepseek-flash`；离线质量审计用的是 `get_chat_llm("precise")`，走同一套 `LLM_PROVIDER` 配置。用同一个模型家族给自己打分，分数会系统性偏高，这是我不否认的。

**第二，我做了哪些工程手段把风险压低（`backend/evals/agent_quality.py`）：**

- Judge 输出**结构化 + JSON Schema 强校验**，不符合结构直接标 `invalid_output` 并跳过，绝不给分——这一条就是之前 100 条里 97 条有效、3 条无效的来源。
- 判断忠实度时要求 claim 级别显式给 `supported` 和 `evidence_ids`，并且**程序校验引用的 evidence id 必须真实存在于输入**，引用到不存在的 ID 直接判无效，不让模型自证。
- **没有来源正文时忠实度标 `null`，不是 0 也不是 1**，避免"无法评估"被算成结论。
- Judge 只跑离线，**不参与线上回答，也不进自进化发布门禁**，所以它的偏置不会污染系统行为。

**第三，缺的东西我说清楚：人工抽检一致率还没做。** 文档里我明确写了"在完成抽检前不得填写一致率"，所以我不会说"Judge 很准"。下一步按 20% 抽检、报告 Cohen's kappa 或一致率，这是把 Judge 从"诊断工具"变成"可信指标"的必经一步。

### Q8. MRR 0.52 算高还是低？

**答：** 在 top-3 检索场景里算"中等偏上，但远谈不上好"。

MRR 0.5 的直觉含义是：正确的那个章节平均排在**第 2 位**左右（1/0.5 ≈ 2）。所以 0.3155 → 0.4995 的提升，本质是"从经常排在第三位甚至掉队，变成经常排第二位"。

它比 Recall@3 多告诉我的信息是：**Recall@3 只看有没有进前三，MRR 看进得够不够靠前。** 我这两个数一起看，得到的结论是"能捞到，但没排到最前面"，说明首条命中率还不够——rerank 有空间。真正理想的状态是 Recall@3 高**且** MRR 接近 1，也就是捞到并且排第一。我现在离那还远。

**会被追问：** 那为什么不直接优化 MRR？——因为医疗场景里"漏掉"比"排第二"严重得多，所以我的第一优先级是 Recall，MRR 是第二层。

## 三、记忆与自进化

### Q9. Shadow Agent 把用户随口一句写进长期记忆怎么办？

**答：** 先说机制，再说怎么撤。

**触发：** 会话首轮和每 10 轮对话各触发一次，**不与意图分类绑定**——影子 agent 自己扫最近几轮对话，判断有没有值得记住的内容。**异步执行，不阻塞用户回答**——记忆是后台的事。

**约束：** Shadow Agent 是一个被刻意做"无能"的 agent：不许调工具、不许写文件、不许推理出用户没说的东西。它的输出被 Pydantic 卡得很死——`kind` 只能是 `preference` / `service_preference` 两个枚举值，单批最多 8 条，value 最长 240 字符（`ShadowMemoryBatch`）。也就是说**"症状/诊断"这类医疗事实在类型层面就没有落库路径**，它想写也写不进去。

落库前还有两道：`validate_untrusted_text` 挡提示注入，以及去重（同 user、同 kind、同 value 且状态未终结的跳过）。

**怎么撤：** `memory_candidates` 表是 source of truth，每行有 `status`（`pending` / `accepted` / `rejected` / `revoked`）和 `expires_at`。所以撤销是两层：

- 置 `revoked` / `rejected` → 读取侧 `load_active_memory_preferences` 直接排除，**已过期的行也排除**；
- Markdown 那份只是投影，删掉重建即可。

**这里我不装：** 目前没有一个面向用户的"记忆管理"界面，撤销要走数据库或管理接口。产品化的话这个必须有——让用户能看见、能改、能删，否则"记忆"在医疗场景里是负担不是卖点。

### Q10. 数据库已经是 source of truth 了，为什么还要投影 Markdown？

**答：** 三个目的，而且它**绝不参与 prompt**。

1. **可审计。** 投影出来的是人可以直接读的 `profile.md` / `preferences.md` / `active_health_context.md` / `health_history.md`。面试时我能直接打开给人看"这个用户我记住了什么"，这比翻数据库有说服力，也方便做人工审核。
2. **可解释。** 用户画像和"近期状态"分离得很清楚：活跃症状在 `active_health_context.md`，已康复的沉到 `health_history.md`——**康复事件从 prompt 里移除，但记录保留**，这样既不会让"上次感冒"继续污染当前对话，也不会丢掉病史价值。
3. **可重建。** DB → Markdown 是单向的，投影失败只记日志、不阻塞请求，任何时刻都能从 DB 全量重建，所以不存在双写一致性问题。

**会被追问：** 那这不就是缓存吗？——不是缓存，是**只读审计视图**。代码注释里我写死了"DB is the source of truth"，投影方向是单向的，就是为了防止有人反过来拿 Markdown 当输入。

### Q11. 系统级自进化里，哪些是自动的？如果全自动上线出问题怎么回滚？

**答：** 我的设计原则是：**自动化的部分只产出候选，能改变线上行为的那一步必须有人。**

自动的部分：

1. 失败案例收集 + 脱敏（`evolution.py`）；
2. 离线 LLM 生成 SkillProposal 草稿，结构化输出 trigger / failure pattern / behavior steps / test case ideas（`evolution_proposer.py`）；
3. **冻结评测集对照**：在隔离环境里跑 baseline 和 candidate 两版，收集质量分、安全违规数、路由回归、cost / latency delta（`evolution_runner.py`）；
4. **发布门禁**（`evolution_eval.py`）：无安全违规、无路由回归、pass rate 不下降、cost delta ≤ 20%、latency delta ≤ 20%，任一不过就拒绝。

必须人工的部分：`approved` 和实际部署。`skill_registry` 是只读的，只认 `SkillDeployment.status == "active"` 且 proposal `approved` 的版本，所以**没有任何一条用户请求能在线改 prompt 或装工具**——模块 docstring 里专门写了这一句。

**回滚是有的：** `POST /deployments/{base_skill}/rollback`（`evolution_api.py`）。因为 Skill 是版本化的、deployment 指向 proposal，回滚就是让 deployment 指回上一个 approved 版本，返回里带 `rollback_supported: true`。

**会被追问：** 门禁阈值 20% 哪来的？——拍的，属于保守默认值。它应该是业务可接受成本的函数，等有真实流量数据再校准。

### Q12. 你对标 Hermes 的自进化，到底吸收了哪一点？

**答：** Hermes 最核心的一点是：**把"用户是谁"从上下文里拎出来，固化成一个可持久、可读、跨会话复用的用户级文件。** 这解决的是"每次对话都从零开始认识你"的问题。

我吸收的就是这一层，但做了三处改造：

1. **写入从"随手写"变成"结构化 + 校验 + 可撤销"。** Hermes 式记忆是模型自由写 markdown，我这边是 Pydantic schema 卡死 + 安全过滤 + 状态机（`accepted` / `revoked` / `expires_at`）。代价是灵活性，换来的是医疗场景能审计。
2. **加了"近期状态"这一层。** 用户近几天反复问感冒，会被识别成一个带 `status` 的健康事件（`active` / `possible` / `resolved` / `archived`），康复后自动从 prompt 移除但保留在历史里。Hermes 的文件模型没有这种时间衰减语义。
3. **往上叠了一层系统级自进化**——Hermes 只改"关于用户的记忆"，我还做"系统自己的能力记忆"：失败案例 → skill 提案 → 冻结集对照 → 门禁 → 人工审核。

**我少的那块也说清楚：** Hermes 是即时自我改写，我是离线 + 门禁。在医疗场景里我认为**在线自改 prompt 本身就是不可接受的风险**，所以我故意不做。这不是能力不足，是取舍。

## 四、安全与评测

### Q13. 确定性规则优先于大模型，会不会误伤正常问题？过度拦截率多少？

**答：** 会误伤，而且我现在有数了。

规则本身是 23 条（`skills/emergency_triage/skill.py`）：CRITICAL 10 条、URGENT 8 条、PROMPT 5 条，另外配了一条否定检测，避免"没有胸痛""否认呼吸困难"被当成阳性。

**过度拦截率（只在明确标注 `NON_URGENT` 的负例上算）：**

| 样本类型 | 数量 | 分级准确率 | 过度拦截率 |
| --- | --- | --- | --- |
| 人工梳理安全集 | 48 | 0.896 | 5.6% |
| 看似吓人实则非急症 | 80 | 0.90 | 10.0% |
| 提示注入 / 对抗性 prompt | 80 | 0.70 | 14.3% |

（来源：`backend/evals/reports/emergency_triage_report_200.json`）

**结论要连着说，不能只挑好听的：** 在原来那 48 条上二分类 F1 是 0.912，但把集合扩到 208 条对抗 + 负例之后，整体 F1 掉到 **0.648**，exact level accuracy 0.822，其中 CRITICAL 的 recall 只有 0.5（34 条里漏了 17 条）。也就是说，**原集合上的漂亮数字有很大一部分是"分布内"的运气**，规则对没见过的表述泛化不够。

顺带解释一个容易误读的数：`scary_but_non_urgent` 那组二分类 F1 显示为 0，不是模型全错，而是这组样本的期望全是负例，Precision/Recall 在这种分组下没有定义。这组真正有意义的指标是分级准确率 0.90 和过度拦截率 10%。

### Q14. 48 条样本的 F1 91.2% 能说明什么？扩到 200 条先补哪两类？

**答：** 说明管线通了，不能说明泛化能力。

n=48、p≈0.91 的情况下，95% 置信区间大概在 [0.80, 0.97] 这个宽度——也就是说"真实水平可能只有 80%"这件事完全在误差范围内。所以我在简历上写这个数的时候，口径必须是"48 条人工合成安全样本"，不能写成"安全能力 F1 91.2%"。

两类样本我已经补了：

1. **提示注入 / 对抗性医疗 prompt**（80 条）——这类攻击会试图让模型绕过急症规则，直接给用药或诊断结论；
2. **"看似吓人实则正常"的负例**（80 条）——专门测过度拦截，比如描述别人的症状、复述电影情节、讨论疾病知识。

补完之后暴露出来的问题就是我上面说的 F1 掉到 0.648。**下一步我会补的不是"更多模板变体"，而是分布外的真实表达**：口语化 / 方言 / 省略主语的短句（"胸口闷得慌"、"喘不上气儿"），以及真实的去标识化问诊记录。模板变体只能测鲁棒性，不能测泛化。

### Q15. 端到端任务完成率 97% 是怎么定义的？会不会过拟合自建集？

**答：** 口径先讲清楚，然后我主动说过拟合的问题。

**"完成"的判定是确定性的**（`evals/e2e_eval.py`）：Graph 正常结束 + final answer 非空 + 期望 Agent 被覆盖 + 没有未处理异常。工具超时、模型异常、Graph 失败一律按 case 记失败，**不允许静默算成功**；如果整轮完整性不足，报告标 `partial` 而不是给一个完整 benchmark 结论。

**结果：** 100 条上任务完成率 97.0%，平均延迟 19.9s，P95 49.5s，路由准确率 **80%**。（`e2e_eval_merged_100_judge_v2.json`）

**过拟合问题我不回避：** 这 100 条是 10 个模板的确定性变体扩展，报告里明确标了 `synthetic_regression_only`，**它不是人工标注的临床数据**。而且路由准确率只有 80%，说明这个 97% 主要说明"链路能跑通"，不代表"每一条都路由对了"。真正有信息量的是那个 80%。

所以我在文档里写死了一句：不能把它表述成"200 条人工标注临床评测"或者"97% 临床准确率"。要往上走，路径是去标识化的真实问诊数据 + 人工标注期望任务和证据锚点，并且核验数据许可。

### Q16. 平均 19.9s、P95 49.5s，如果要求 P95 压到 8s，你先砍哪块？

**答：** 按性价比排，我砍的顺序是：

1. **先砍 Agentic RAG 的多轮检索。** 它是延迟主因：消融里单轮 4.6s、三轮 28.1s，而来源级 Recall 只差 1pp。绝大多数问题单轮 + 重排就够，只有控制器明确报告 `missing` 非空时才进第二轮。这一刀能砍掉最可观的一块延迟，质量损失最小。
2. **把 rerank 换成小模型或交叉编码器。** 现在用 LLM 重排，延迟高、还贵；top-10 以内的重排用轻量 cross-encoder 完全能打。
3. **并行 + 缓存。** executor 已经是 DAG 分批并发；再加 Redis 语义缓存（项目里已有 cache 层）覆盖高频重复问题。
4. **意图识别和 planning 用小模型。** 这两个是结构化输出任务，不需要最强模型。

**我不会砍的：** 确定性安全规则和 verifier 门禁。这两块是几乎零延迟的，砍它换不来性能，只会换事故。

**会被追问：** 那自进化呢？——自进化全在离线，根本不在请求链路上，砍它不影响 P95。

## 收尾两题

### Q17. 这个项目里最重要的一次技术取舍是什么？

**答：** 放弃"在线自进化"，改成"离线提案 + 冻结集对照 + 人工审核 + 可回滚"。

最省事的做法是让系统发现失败就自己改 prompt / 装 skill，Hermes 那种即时自我改写也很性感。但医疗场景里，一次错误的自动改写可能直接变成一次错误建议，而且**你事后根本不知道是哪个版本改坏的**。

所以我牺牲了自适应速度，换三样东西：可审计（每次改动都有 proposal 和评测证据）、可回滚（版本化 deployment + rollback 接口）、可追责（门禁不通过就不上线）。

第二个取舍是接受延迟换质量：Agentic RAG 用 4.6s → 28.1s 的代价，换来章节级 Recall@3 +0.17。当时我认为在医疗场景里"少漏证据"比"快几秒"重要，但如果产品是面向 C 端的高频轻问诊，这个取舍我会反过来做。

### Q18. 如果现在让你砍掉一个模块，你砍哪个？

**答：** 产品维度上砍医保 Agent。

理由：它跟"健康咨询"主链路的耦合最弱，依赖外部数据源、合规要求最重，而它贡献的演示价值最低。砍掉之后 Supervisor 少一个能力域，planner 的 DAG 更简单，路由准确率也能受益——现在路由准确率只有 80%，能力域越多越容易分错。

**评测维度上砍 500 条的合成 RAG 集。** 它是 100 条的确定性 5 倍扩展，只能证明"代码不会崩"，不能提供任何新增信息，留着反而容易被当成"我扩充了数据集"的注水证据。我宁可把精力花在补 100 条里真正难的长尾 case。

## 已知短板（主动说，别等着被挖）

1. **路由准确率只有 80%**，是端到端链路里最弱的一环，比"完成率 97%"更能说明系统真实水平。
2. **LLM-as-a-Judge 没有人工校准**，一致率空白，Judge 与线上模型同源，存在自评偏置。
3. **Agentic RAG 的控制器偏保守**，`sufficient_rate` 0.62，经常耗到 max_rounds，延迟代价大。
4. **安全规则的泛化不足**，扩集后 F1 从 0.912 掉到 0.648，CRITICAL recall 只有 0.5。
5. **没有面向用户的记忆管理界面**，撤销记忆需要走数据库或管理接口。
6. **消融实验没有做显著性检验**，单次运行、单数据集。

这六条里，第 1、4 条我认为是当前最值得先修的：一个决定用户体验，一个决定安全底线。
