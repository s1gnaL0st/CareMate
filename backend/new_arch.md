

# 大健康 App 多智能体系统架构设计

## 一、核心设计思想：从“路由器”到“监督者”的升维

原版方案采用扁平化的“意图路由”（Router），只能做单次、单选的分流，无法处理复合意图且缺乏全局管控。

**本次重构的核心演进路径：**
> **Router（接线员） → Supervisor（私人健康管家）**

Supervisor 不再是简单的“转发器”，而是**全流程的编排者与决策者**。它负责理解用户的完整诉求，拆解任务，调度专家，验证结果，并在出错时自主纠偏。

## 三、核心运行引擎：Plan-Solve-Verify-Replan 闭环

这是系统的“大脑与心脏”，所有逻辑围绕这个无限循环运转。

### 1. 标准流程（正常情况）

| 阶段 | 执行者 | 核心动作 | 产出 |
| :--- | :--- | :--- | :--- |
| **Plan（规划）** | Supervisor（调用强LLM） | **前置意图过滤**（闲聊/健康/紧急）+ **任务拆解**（生成依赖队列） | 结构化JSON任务队列 |
| **Solve（执行）** | Supervisor（调度）+ 各子Agent | 按依赖顺序串行/并行调用原子Agent | 各Agent结构化输出 |
| **Verify（验证）** | Supervisor（轻量LLM + 硬规则） | 三重检查：逻辑一致性 / 信息完整性 / 安全红线 | Pass / Partial / Fail |
| **Replan（重规划）** | Supervisor（自主纠偏） | 根据Verify结果动态修正路径（见下文详述） | 补充任务 或 全新队列 或 安全熔断 |

### 2. Plan阶段的“前置意图过滤器”（第一道关卡）

| 分类 | 判定特征 | Supervisor 行动 |
| :--- | :--- | :--- |
| **紧急（Emergency）** | 胸痛、窒息、中风迹象、严重外伤 | **阻断所有Agent**，直接输出急救话术，强制结束本轮 |
| **纯闲聊（Pure Chat）** | 问候、情绪宣泄、乱码、测试性输入 | 仅生成任务 `[{"agent": "chat_agent"}]`，**严禁调用专业Agent** |
| **混合意图（Mixed）** | 闲聊中夹带健康问题（如“你好，我头疼”） | **丢弃闲聊部分**，仅对健康部分进行任务拆解 |
| **健康相关（Health）** | 提及症状、药品、报告、医保、体检数据 | 进入正常的多任务拆解流程 |

### 3. Replan（重规划）的三种触发类型与对策

| 触发类型 | Verify结果 | 典型场景 | Supervisor 应对策略 |
| :--- | :--- | :--- | :--- |
| **增量补丁（Patch）** | **Partial（信息缺失）** | 医保Agent只查了余额，但用户问的是报销比例 | **保留**已有正确结果，只生成**1个补充任务**插入队头，继续执行 |
| **完全重置（Hard Reset）** | **Fail（逻辑矛盾）** | 症状评估推荐“耳鼻喉科”，但科普检索说该症状指向“心内科” | **丢弃**本轮所有冲突结果，携带错误日志**重新执行Plan** |
| **安全熔断（Safe-Break）** | **Fail（红线违规）** | 输出含“包治百病”或自伤信息，或严重偏离临床指南 | **丢弃所有结果**，不再调用AI，直接**转接人工客服** |

**工程保护三把锁（防死循环）：**
- **次数锁**：单轮会话最多允许 **2次** Replan，超限强转人工。
- **内容锁**：若两次Plan生成的队列**完全一致**，判定为死循环，触发熔断。
- **时间锁**：总处理时间超过 **8秒**，立即中断并输出兜底话术。

## 四、原子 Agent 集群定义（6个）

经过严格的**去冗余**和**物理隔离**设计，最终定型以下6个职责唯一的Agent：

| 序号 | Agent名称 | 核心职责（唯一） | 严格禁止的红线（隔离规则） |
| :--- | :--- | :--- | :--- |
| **1** | **症状评估Agent** | 结构化收集症状 + 紧急分级（绿/黄/红）+ 推荐挂号科室 | **严禁**给出用药建议或最终疾病诊断 |
| **2** | **科普检索Agent** | 纯RAG检索权威医学库（药品/疾病知识） | **严禁**进行个性化推荐（如“你适合吃这个药”） |
| **3** | **单次报告解读Agent** | 提取上传化验单的异常指标，匹配临床参考值 | **严禁**关联历史数据做趋势预测 |
| **4** | **健康趋势分析Agent** | 分析时序健康数据（血压/血糖等），发现波动拐点 | **严禁**解读单次报告，仅看长期趋势 |
| **5** | **医保事务Agent** | API/RPA调用：查余额、算报销比例、异地备案 | **严禁**回答“这个病贵不贵”等医疗价值推测 |
| **6** | **通用对话Agent** | 处理所有非健康相关的社交闲聊、乱码 | **严禁**调用任何医疗数据与知识库 |

## 五、关键设计原则（三位一体保障）

### 1. 去冗余（职责互斥）
- 每个Agent的职责边界用**自然语言+代码契约**双重锁定，确保任何两个Agent的工作内容**零重叠**。
- 原`advisor_agent`被拆解：个性化建议上移给Supervisor，自身退化为纯“科普检索Agent”。

### 2. 隔离性（物理与逻辑隔绝）
- **契约隔离**：每个Agent的输入输出强制使用 `Pydantic` 固定字段（代码级硬约束）。
- **上下文隔离**：Solve阶段，Agent只能看到Supervisor传给的**专属Input Slice**，无法窥探其他Agent的历史记录。
- **工具链隔离**：`医保Agent` 只挂载医保API，`科普Agent` 只挂载向量数据库，底层网关对越权调用直接报错阻断。
- **存储隔离**：输出写入记忆池时带 `agent_name` 前缀（如 `symptom.result`），其他Agent无权跨域读取。

### 3. 容错与熔断
- **空值熔断**：任一Agent返回 `NULL`，**禁止**Supervisor用AI幻觉补全，必须走重试或兜底。
- **超时熔断**：任一Agent执行超时，立即中断并触发Replan或人工转接。

## 六、完整端到端数据流示例（复合意图）

**用户输入：** *“你好，我最近三个月血压从120升到150，想吃降压药，不知道医保能不能报？”*

| 步骤 | 执行层 | 动作拆解 | 说明 |
| :--- | :--- | :--- | :--- |
| 1 | Supervisor（Plan） | 前置过滤器判定为 **混合意图** → 丢弃“你好”，仅保留健康部分 | 闲聊不占用专业资源 |
| 2 | Supervisor（Plan） | 强LLM拆解任务队列：`[趋势分析, 科普检索, 医保事务]` | 按逻辑依赖排序 |
| 3 | Supervisor（Solve） | 串行调用 Agent4（趋势）→ Agent2（科普）→ Agent5（医保） | 三者数据完全隔离，互不可见 |
| 4 | Supervisor（Verify） | 检查：科室推荐 vs 药品信息 vs 报销比例，三方是否逻辑自洽 | 无矛盾则Pass |
| 5 | Supervisor（聚合） | 按“健康预警 → 药品须知 → 支付政策”顺序组织最终回复 | 风格统一，逻辑清晰 |
| 6 | Supervisor（记忆） | 更新用户画像：记录“血压异常波动”及本次对话摘要 | 供下次主动关怀使用 |

## 七、技术栈落地建议（参考行业实践）

| 层级 | 选型建议 | 理由 |
| :--- | :--- | :--- |
| **编排与控制层** | **LangGraph** | 比AutoGen更适合确定性工作流，成本可控，可观测性强（已验证的行业选择） |
| **子Agent实现** | 普通Python类 + LangChain工具链 | 轻量、解耦、便于单元测试 |
| **契约校验** | **Pydantic V2** | 强制入参出参类型检查，物理层面杜绝数据污染 |
| **记忆池** | Redis（会话级）+ PostgreSQL（用户画像） | 兼顾高速读写与持久化 |
| **模型分层（降本）** | Plan/Verify用GPT-4o；Solve中`chat_agent`用GPT-3.5-turbo | 预估可节省30%+ Token成本 |

## 八、总结

这套架构的核心灵魂在于：

> **Supervisor 负责“动脑”（规划与验证），子Agent 负责“动手”（执行具体事务），Replan 负责“纠偏”（自主修复错误）。**

它完成了从**被动响应**到**主动管理**的质变，彻底解决了原版设计意图重叠、缺乏紧急处理、无法应对复合问题的硬伤。现在，你已经拥有了一套**高内聚、低耦合、带自愈能力**的生产级大健康智能体系统蓝图。
